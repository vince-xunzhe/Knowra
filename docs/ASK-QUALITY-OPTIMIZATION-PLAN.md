# Ask 检索与证据质量优化计划

> 状态：评测基础已合并；原文证据层与编译保真／claim 归因层已形成未发布的本地依赖提交；混合 claim/source 检索正在新的隔离 worktree 完成 shadow 验收。真实研究数据、运行服务、现有 Wiki／FTS 和 Ask 回答均未改动。
> 原则：先定位损失层，再修改该层；不以单个问题的字符串规则冒充系统能力。

## 1. 问题定义

Ask 的目标不是“搜到含有几个关键词的文件”，而是：

1. 原文中的关键事实被忠实提取，并保留原文定位；
2. 论文页和跨论文概念页没有静默丢失回答所需的信息；
3. 检索能召回并正确排序含有相关证据的材料；
4. 回答中的每个重要 claim 能回指证据，证据不足时正确拒答；
5. 上述质量提升在可接受的延迟、token、存储和维护成本内完成。

当前代码链路是：

```text
PDF → 结构化抽取 → 论文 Wiki → 概念 Wiki → 文档级 FTS/图检索 → Ask 回答
```

每一箭头都可能造成损失。端到端一次失败不能直接证明是哪一层出错，单元测试全绿也不能证明真实研究问题已解决。

## 2. 已知事实与尚未验证的假设

### 已知事实

- 当前 FTS 只索引编译后的论文/概念 Wiki，不索引原文页面、结构化抽取字段或 claim 证据。
- 当前 Codex CLI 检索是有预算的确定性编排；它不会先由模型理解问题后再自主规划多轮概念检索。
- 当前 Wiki 引用是文件级，不能稳定定位到论文页或支持某一具体论断的原文片段。
- 已观察到的两种跨论文演进问法在生产检索路径上可能严格零命中，即使合成 Wiki 正文含有核心词。
- 当前概念 Wiki 的编译输入没有覆盖全部结构化字段，特别是创新、历史位置、实验增益和局限等演进问题常用信息。

### 尚未验证

- 真实论文的关键事实主要丢在 PDF 抽取、结构化抽取、论文 Wiki，还是概念 Wiki。
- 真实候选文档的相关性、排序质量以及足够回答问题的 claim 覆盖率。
- 语义 embedding、reranker 或结构化 claim 检索分别能带来多大增益。
- 在正确证据已经提供时，当前回答模型的综合和引用质量是否仍是主要瓶颈。

因此，第一轮不会直接选定“向量库”或重新编译所有资料，而是先建立能区分这些假设的评测协议。

## 3. 评测协议

### 3.1 数据集

维护两套互不混淆的数据：

- **公开合成集**：可提交仓库，覆盖精确标题、正文实体、别名、同义表达、跨论文演进、多概念、排序、无答案和编译信息损失。
- **本地私有评测集**：30–50 个真实研究问题，人工标注相关 paper ID、必要 claim 和页/章节；不提交问题上下文、论文正文、标题或标注结果。

问题类别至少包含：定义、机制、比较、演进、关系、实验数字、局限、矛盾和无答案。

### 3.2 Oracle 对照

每题至少做四个对照：

| 对照 | 目的 |
| --- | --- |
| 提供正确原文片段 | 判断回答/综合上限 |
| 提供正确结构化抽取 claim | 判断原文抽取后的信息是否足够 |
| 提供正确论文/概念 Wiki | 隔离检索与 Wiki 编译损失 |
| 使用实际检索结果 | 测量召回、排序和最终证据覆盖 |

若原文 oracle 能回答而结构化抽取不能，问题在抽取；若结构化抽取能而 Wiki oracle 不能，问题在编译；若 Wiki oracle 能而实际检索不能，问题在召回/排序；若正确证据输入后仍答错，问题在综合或证据门槛。

### 3.3 指标

| 层 | 核心指标 |
| --- | --- |
| 原文→抽取 | 关键事实覆盖率、字段精确率、证据片段蕴含率、页码准确率 |
| 抽取→论文/概念 Wiki | 支持 claim 保留率、演进字段保留率、来源签名新鲜度 |
| 检索 | Recall@k、Precision@k、MRR、nDCG@k、无答案准确率 |
| 证据 | 必要 claim 覆盖率、错误来源率、相互矛盾证据覆盖 |
| 回答 | claim 支持率、引用页准确率、完整性、矛盾率、拒答正确率 |
| 成本 | p50/p95 延迟、模型调用/token、索引大小、编译和重建时间 |

所有报告必须写明 `measured` 与 `not_measured`。合成检索通过不能表述为真实语料端到端成功；真实私有评测也不能把未标注文档自动视为不相关。

## 4. 分轮实施

第一轮从已合并的最新 `origin/main` 建立隔离 worktree；后续轮次使用新的隔离 worktree 和按依赖串联的本地分支／提交，不触碰原 checkout、真实数据或运行服务。每轮使用独立合成数据并完成独立审查，但在最终端到端验收通过前不创建、推送或发布任何本次迭代 PR。只有全部轮次达到最终目标后，才一次性发布可审查的 PR 链；若最终验收失败，本次迭代不发布任何 PR。用户仍负责合并，系统不得自动合并或部署。

### 第 0 轮：分层评测基础（本轮）

范围：

- 用生产 `wiki_search` 实现建立一次性 FTS5 索引；
- 合成 fixture 以稳定 claim ID 标注 source、extraction、Wiki 和 query；
- 报告 oracle 上限、Recall/Precision/MRR/nDCG、claim 覆盖、拒答和延迟；
- 纳入两种已观察失败形态，以及精确标题和无答案控制组；
- 固化校验规则，避免缺失相关文档、相互矛盾标签产生虚假成绩。

不做：模型调用、真实数据读取、语义检索、重新编译、迁移或服务启动。

验收：评测能明确区分“Wiki 已有证据但检索没找到”和“即使 oracle 检索也因 Wiki 丢失 claim 而无法回答”。

### 第 1 轮：可追溯证据层

目标：让 Wiki 不再是唯一证据源。

- 设计不可变的页面/章节 evidence chunk：`paper_id/page/section/text_hash/parser_version`；
- 为结构化字段增加 claim 与 supporting span/quote，保留 extractor 版本；
- 先对合成 PDF 和少量公开 fixture 双写验证，不迁移真实数据；
- 保持现有 Paper、Wiki 和 API 兼容，新增能力可关闭、可回滚。

DoD：页面覆盖、定位准确率、重复构建确定性和旧数据兼容通过；没有真实数据迁移。

### 第 2 轮：编译保真与新鲜度

目标：论文/概念 Wiki 成为可解释的派生视图。

- 用字段/claim 预算替代单一字符串截断；
- 概念页纳入创新、历史位置、实验增益、局限和建模变化；
- 生成内容保留 supporting claim IDs，页面引用可下钻；
- 编译签名绑定实际抽取内容、模型和模板版本；
- 在影子目录编译，不覆盖现有 Wiki。

DoD：合成和公开小语料的 claim 保留率达到约定阈值，过期检测准确；仍不触发真实全量重编译。

### 第 3 轮：混合召回与排序

目标：从问题意图召回证据片段，而不是只搜整篇摘要。

- 保留 BM25/FTS 作为精确术语和数字通道；
- 增加 evidence chunk/claim 的语义召回，以及实体、关系、时间和 claim 类型过滤；
- 使用可解释的 rank fusion，必要时增加轻量 rerank；
- CLI 与 API 共用有界 planner：一次规划、并行召回、一次缺口补检、一次综合；
- 严格记录每路候选、最终排序、预算与降级原因。

不预设大型向量数据库；当前规模先验证 SQLite 本地索引或轻量本地向量表是否足够。embedding 的本地/云端选择必须保持 local-first 隐私边界。

DoD：在公开合成集和本地私有标注集上，相对词法基线提高 Recall@k 和必要 claim 覆盖，同时无答案准确率不显著退化；报告 p95 延迟和存储成本。

当前 shadow 进展（未激活）：签名 claim ledger、validated evidence chunk、独立 SQLite FTS、可插拔预计算向量、RRF、最终 top-N coverage、一次 gap、CLI/API 共用执行器及硬预算已由合成回归覆盖。长中文演进问法的固定 fixture 从词法 Recall@4=0.00 提升到 hybrid=1.00；这不代表真实语料成功。真实 dense 模型、私有标注集、p95 和 no-answer 阈值尚未测量，因此生产 Ask 保持原状，所有候选仍报告 `answerable=false`。

### 第 4 轮：claim 级回答与引用

目标：回答门槛从“读过一个文件”升级为“主要结论都有证据”。

- 综合输入使用紧凑 evidence spans；
- 每个主要 claim 绑定论文、页/章节和 supporting span；
- 演进问题要求覆盖至少两个可比较阶段；
- 冲突证据显式呈现；证据不足继续拒答；
- 对正确证据 oracle 和实际检索分别评分，避免把检索缺陷算到模型上。

DoD：claim 支持率、引用定位准确率、完整性和拒答正确率达到约定阈值；不得只凭语言流畅度验收。

### 第 5 轮：私有影子验证与可选重编译

只有前四轮指标证明新链路有实质增益，才讨论真实资料重编译。先在隔离目标中做影子编译和人工抽检；用户批准后才允许切换。

## 5. 真实数据重编译前的备份与恢复门禁

本轮没有执行备份，也没有读取或改动真实资料。真正需要重编译时，必须先由用户确定备份目标、加密、保留周期和维护窗口，然后执行独立任务：

1. 盘点并记录版本和只读计数；
2. 先选择并获批一致性方式：暂停 API 和独立 worker，或使用能覆盖数据库与文件资产的同一文件系统快照；记录 generation/队列状态，未经批准不得自行停服务；
3. 对活跃 SQLite 使用 backup API 取得一致快照，不直接忽略 WAL 复制；若数据库与文件分别快照，必须在前后再次核验 generation、文件清单和任务状态均未变化，否则整次备份作废；
4. 备份：
   - `data/knowledge.db`、`tasks.db`、`recommendations.db`；
   - `data/papers/`、`paper_records/`、`wiki/`；
   - `wiki_search.sqlite` 等可重建索引，标明其可重建属性；
   - 用户批准的配置/偏好以单独加密方式处理，绝不进入 Git；
5. 排除 `.venv`、`node_modules`、`.cache`、构建产物、日志和进程锁；
6. 为备份生成文件清单、大小、SHA-256 和数据库完整性结果；
7. 在另一个隔离 worktree/数据目录恢复，禁用外部 provider 和任务执行；
8. 验证数据库完整性、论文/记录/Wiki 数量、资源引用、抽样文件哈希及同一 generation 的跨资产一致性；
9. 影子重编译写入新目录/新索引，旧生成物保持不变；
10. 对比通过并再次获得批准后才原子切换，保留旧 generation 作为即时回滚点。

任何需要停服务、暂停 worker、覆盖目录、迁移数据库或切换索引的动作都必须在执行前报告具体影响并等待批准。

## 6. 成本和停止条件

- 页面 evidence 会增加存储，但在证明召回收益前不全量生成 embedding。
- claim 抽取和 rerank 会增加模型成本，应分别做消融，不能打包后只看总分。
- 混合检索若没有显著提高 Recall@k/claim 支持率，或 p95 延迟超出约定预算，应回退该通道，而不是降低证据门槛。
- 精确词法检索必须保留；语义检索的误召回需要 no-answer 和 hard-negative 集约束。
- 在私有标注集完成前，不宣称“彻底解决”真实跨论文问答。

## 7. 决策门槛

每一轮本地验收记录（以及最终发布的每个 PR）必须回答：

1. 改动针对哪个已测量的损失层？
2. 相对哪个固定基线改善了什么指标？
3. oracle 上限是否说明另一层仍是瓶颈？
4. 对延迟、token、存储、隐私和维护成本有什么影响？
5. 如何关闭、回滚，是否需要真实数据备份？

缺少上述证据时，不进入下一轮真实数据迁移或全量重编译。
