# 个性化论文推荐：首版设计与实施边界

日期：2026-09-23。最新决定：用户已选择完整本地优先。桌面画像、调度、队列、反馈和 Codex CLI 均在本机运行，无需云登录或 Fly.io；以后再迁移 SSH 主机。下文保留访谈中的算法设计，云端部分仅作为可选扩展，实际边界见第 11 节及运行手册。

## 1. 已确认的产品选择

| 项目 | 用户确认的要求 |
| --- | --- |
| 推荐目标 | 长期兴趣为主，当前课题为辅，保留少量跨方向探索 |

## 2. 当前工程的可复用部分与缺口

- `backend/services/recommend_service.py`：固定主题检索、周一/三/五调度与补跑基础。实际保留期限是 7 天，部分注释仍写 30 天；首版不能依赖这个短期表保存长期反馈。
- `backend/services/arxiv_service.py`：已有标题、摘要、作者、类别、发表时间获取逻辑。当前只取检索首批，固定上限，且 arXiv ID 保留版本号。扩大候选池需要分页、时间窗口、断点和统一标识。
- `backend/models.py`：论文分类、团队、知识节点、标签以及来源论文关联可以复用。桌面画像使用当前工作区的本地论文和可见知识节点；可选云模式仅使用该用户已同步的数据。
- `backend/cloud_models.py`、`backend/routers/cloud.py`：已有公共推荐数据、用户收藏与云端接口，尚无个人推荐批次及采纳事件链路。
- `frontend/src/pages/RecommendPage.tsx`、`mobile/src/screens/RecommendScreen.tsx`：已有推荐列表、收藏和摘要展示，可增加精选、解释与任务状态。
- `model_gateway/runtime.py`：已有 API / CLI 文本调用入口。现有 embedding 入口依赖 API，不能作为 CLI-only 测试的必需步骤。
- `backend/routers/papers.py` 的推荐下载接口：目前仅保存 PDF，后续目录扫描才入库。必须区分“收藏”“下载”“入库成功”。

以上为实施前的代码检查记录；本地验证结果见运行手册。尚无真实用户推荐质量基线。

## 3. 推荐流程

### 3.1 建立可追溯的多维画像

从已有结构化知识和论文元数据中提取：研究领域、问题/任务、技术路线、方法、数据集和团队。每条特征保留来源论文、证据和置信程度。

每篇论文对初始画像的总贡献相同；一篇论文包含多个标签时归一化贡献，避免标签多的论文自动获得更大权重。自动生成的多个知识节点也不能让同一来源论文被重复计数。已有人工作出的分类、团队修正优先于自动判断。

画像分为长期兴趣、近期研究意图和后续采纳偏好三个部分。手动课题只覆盖近期意图，不抹掉长期兴趣。删除/修正论文可触发画像重算，但删除不能被默认为“不喜欢”。

数据集和团队不一定出现在摘要中：允许未知，不让模型补造。团队优先来自已有作者—团队映射，明确标注为匹配结果；不能仅凭作者姓名认定实际机构归属。候选特征中要区分“使用某数据集”和“仅提及某数据集”。

推荐阶段不重新解析库内全文。缺失信息先使用已有结构化结果、标题或可获取的摘要，并记录缺失程度。用户采纳之后的普通论文入库处理继续遵循现有流程。

### 3.2 用多路检索扩展候选范围

从长期画像、当前课题和相邻方法产生有限、可追溯的 arXiv 检索词。公共学科检索与个性化检索合并，避免固定的现有主题成为唯一入口。

新论文增量抓取和历史补漏分别维护游标；处理分页、限流、重试、重叠时间窗口与去重，避免只取最新首批而丢失候选。历史检索按需进行，不为“海量”预先下载全站数据。

以去除版本号的 arXiv base ID 作为论文身份，保留版本与内容摘要哈希。不同检索词命中同一论文合并；摘要内容更新时才重新提取特征。跨版本只允许一次入库采纳。

### 3.3 先粗筛，再对有限候选精排

首版采用“内容匹配 + 个人正向反馈 + 有限 AI 精排”。无需其他用户行为或协同滤波，也不要求训练专属大模型。

1. 用文本检索、分类/作者匹配和已缓存特征做粗筛。CLI-only 路径可使用本地词项检索与结构化标签，无需 API Key 或新增 embedding 服务。
2. 只对进入短名单且未缓存的论文做 AI 特征提取；同一论文的公共特征可复用，含用户画像的评分与解释保持用户隔离。
3. AI 使用候选元数据与用户画像，输出结构化相关性、匹配维度、证据和不确定性。输出校验不通过时有限重试，仍失败则保留可解释的基础排序结果或延期，不伪造 AI 评分。
4. 程序执行最终约束：排除已入库、去重、相关性门槛、同方向/同团队适度分散，以及长期/近期/探索的分配。模型不能直接写库或更改推荐算法。

Embedding 保留为可插拔增强项；启用 API 路径并明确配置后再使用。同一任务的 API 与 CLI 共用输入、输出 schema 和缓存契约，切换后不保证模型结果完全一致。

精选卡片应说明“为什么与你相关”，展示具体匹配维度和少量相关库内论文，并注明长期兴趣、当前课题或探索来源。只从摘要得出的判断不能包装成全文评审或学术质量认证。

### 3.4 将真实入库转化为反馈

记录生成、展示、浏览和成功入库事件，关联用户、论文、推荐批次、画像版本及排序版本。浏览事件服务于产品评估，不用于暗中推断负向兴趣。

“加入知识库”操作必须在知识库记录成功落库后才产生采纳。下载失败、等待扫描、重复下载不算新采纳；后续全文解析失败与入库成功分开记录。采纳事件通过唯一约束和幂等键防止重复计算。当前桌面记录在本机，跨设备同步作为后续扩展。

现有手机收藏仍是暂存。若首版提供手机“加入知识库”，建议先创建待入库请求，显示待执行状态；真实入库完成后再确认采纳。不能把一个手机收藏请求当成已成功入库。

所有新增入库论文都会进入基础兴趣画像，但只有可关联到推荐曝光的入库才计入推荐采纳指标。一次采纳带来的基础画像变化和额外偏好调整应有明确、有限的贡献，避免重复放大。

### 3.5 定期更新，保持变化可追踪

每次推荐使用最新可用的库内结构化信息与当前课题。更慢的周期性任务结合新增采纳更新检索词和特征偏好；没有新反馈时不做无意义的模型调用。

首版用带平滑、变化幅度限制的正向特征更新：新增采纳适度提高对应方法、问题、数据集或团队的偏好，仍以全库长期画像为主要依据。未采纳候选不构造为负样本，也不把它们自动放进成对排序训练。

保存画像/参数版本、变动来源和前后差异。样本不足时保持已有参数；参数异常、相关性或多样性明显退化时回到上一版本。首版不声称“每次更新必然提升效果”。

## 4. 本机调度与后续远端执行节点

默认由本机 SQLite 保存周期计划、候选库、个人推荐批次、事件和队列；worker 直接读取本地库并提交经过校验的结果，不经过 HTTP、JWT 或云数据库。桌面后端自动启动 worker。后续可把服务、知识库及推荐数据库整体迁移至 SSH 主机，通过 SSH 隧道访问。已有的云队列/远端 worker 路径保留为显式可选模式，手机使用该模式；两种模式的画像和反馈暂不自动合并。

使用持久化任务与租约，避免 Web 服务重启、多进程或重试生成重复批次。任务包含用户、类型、时间槽、输入哈希和版本，结果写入要求幂等，并拒绝过期租约的迟到结果。

心跳反映节点存活；另做模型能力/调用健康检查，区分离线、CLI 未就绪、认证失效、额度受限和任务失败。站内明确显示最近成功运行时间、延迟原因及最后一次成功精选，不把旧内容伪装成新批次。

离线时保留任务等待恢复，恢复后按有界补跑策略处理，不重复发布已经完成的批次。同一事件在站内合并展示；不发飞书或邮件，不自动切换到付费 API。

节点使用自身配置的模型身份，云端不接收用户本机的 CLI 认证文件。候选标题/摘要作为不可信数据输入；执行节点不应允许论文内容触发任意 shell、外部工具或修改文件。现有 prompt 中“不要执行工具”不能替代执行层能力限制。

## 5. 调用配置与费用控制

增加独立推荐任务绑定，例如画像、候选特征、精排，复用现有模型网关，不继续借用 wiki 编译任务的模型设置。默认继承用户已有 CLI 模型选择，不写死新模型。

本地支持手动执行同一任务流程和本地 worker，默认 CLI；测试不会因 CLI 失败而偷偷调用 API。远端节点可显式选择 API 或 CLI。CLI 结构化输出和用量事件按已安装版本进行能力检查，网关外仍保留 schema 校验。

每用户 ¥30/月约束可计费调用；共享候选提取还需要独立公共任务预算，不能将公共成本重复记给用户，也不能遗漏。API 调用前预留可估算费用，计入失败重试和并发在途调用，调用后按实际可用数据结算；缺少可靠价格或用量时不能保证精确人民币硬上限，应限制或暂停该付费路径。

CLI 的认证/计费模式尚未读取确认。若使用订阅登录，单独展示调用/token用量和额度受限状态，不能按 API 单价认定真实账单；若使用 API 计费则纳入费用预算。CLI 路径另设批次、并发和重试上限，避免消耗不可控。

遇到预算或额度限制，可显示明确标记的基础排序结果，或继续展示上一次精选及延期状态；不把未执行的 AI 精排记为完成。

## 6. 建议默认值：尚未逐项确认，可配置

| 参数 | 首版建议 | 目的 |
| --- | --- | --- |
| 推荐时间 | Asia/Shanghai，周一/三/五 09:00 | 明确用户时区，避免直接沿用 UTC 日期造成偏移 |
| 常规批量 | 每批最多 10 篇，低于门槛可少于 5 篇 | 遵守不凑数要求 |
| 兴趣分配 | 长期/近期/探索约 70%/20%/10% | 表达已确认优先级；小批次按多批累计实现，不机械凑名额 |
| 历史补漏 | 每批至多 2 篇，包含在总名额内 | 与兴趣分配是两条独立维度 |
| 近期窗口 | 近 30 天入库；新论文默认近 30 天发表 | 清楚区分用户活动时间与论文发表时间 |
| 无当前课题 | 无手动描述且近期证据不足时，将近期名额给长期兴趣 | 不捏造短期目标 |
| 参数更新 | 每周检查，新增采纳达到 3 篇才调整；否则继续积累 | 区分知识库画像刷新与反馈参数更新 |
| AI 精排规模 | 粗排前 30 篇中按多样性选最多 12 篇 | 从小规模实测耗时、额度、效果后再调 |
| CLI 并发 | 每节点 1 个模型任务，有限重试 | 控制额度和超时影响 |
| 心跳 | 每 60 秒一次，连续 5 分钟未收到视为离线 | 避免短暂网络波动频繁变更状态 |
| 曝光冷却 | 浏览或展示过的论文 30 天内不重复精选 | 减少重复；冷却不是负向偏好标签 |
| 反馈评估窗口 | 首次有效浏览后观察 14 天入库情况 | 容纳延迟采纳，过早数据标为未成熟 |
| 元数据/事件保留 | 首版建议 180 天；画像证据和入库身份单独长期维护 | 支持历史补漏与评估，不随当前 7 天 feed 清理 |

手机待入库交互、画像解释页和参数设置入口也属于本草案建议，尚非逐项确认的 UI 规格。

## 7. 数据与接口边界

建议按职责引入以下实体，具体表名在实施时与现有 schema 对齐：

- 公共论文及特征缓存：base ID、版本、标题/摘要/作者、证据、提取模型及内容哈希；跨标签引用同一论文。
- 用户画像及版本：长期画像、自动近期画像、手动当前课题、反馈参数、更新时间及来源。
- 个人推荐批次和条目：时间槽、排序、推荐理由、候选来源、画像/参数版本、生成状态。
- 行为与采纳事件：稳定论文身份、曝光/浏览、来源批次、成功入库、幂等标识；不因候选 feed 清理而丢失。
- 节点与任务：能力、心跳、授权范围、队列、租约、重试和站内故障事件。
- 调用与预算：任务类型、provider、模型、可获取用量、可计费费用、未知状态及预算预留。

公共元数据可复用；画像、理由、事件、批次、任务载荷必须用户隔离。数据库策略与应用层均检查用户归属，worker 只取得完成当前授权任务需要的数据。

个人精选接口与现有公共 feed 并存，便于保留浏览能力和基线。加入画像/当前课题、精选批次、行为事件、入库状态和节点状态接口；手动刷新需去重和节流。

## 8. 验收与评估

### 产品指标

主目标为实际浏览精选的 14 天入库转化率至少 30%，对应每 10 篇约 3 篇。它是产品目标，不是已测得的结果，也不是给未采纳论文贴负标签。

有效浏览建议用打开论文详情定义；卡片曝光单独记录。除浏览后转化外，同时报告每批全部精选的采纳数、详情打开率、独立论文数量和样本量，防止只统计少量被打开的论文造成指标虚高。同一用户/论文去重，跨设备事件合并。

记录从推荐到入库的延迟、主题覆盖、重复率、历史补漏比例、每批耗时、费用/CLI 用量及定时任务成功率。保存真实排序版本，并显示尚未完成观察窗口的数据。

### 离线基线与局限

先评估现有时间排序和新的确定性内容排序，再评估添加 AI 精排后的结果；记录相同候选集、数据时间范围、成本和结果。没有现成标注时，不报告虚构的提升百分比。

可将历史入库记录按时间做回放：只用当时已经入库的论文建立画像，检验后续入库论文的召回和排序位置。严格过滤未来知识节点/画像信息；没有真实浏览日志时，回放只能作为代理指标，不能替代 30% 在线采纳目标。候选是否可在当时被检索到也要单独记录。

未采纳候选保持未标注。仅有正反馈时，采纳率变化还受曝光选择、论文供给和用户活跃度影响，不能直接声称参数更新造成了提升。首版固定评估集和窗口，分阶段记录变化，不改已有项目验证划分。

### 必须覆盖的工程检查

1. API / CLI 输出契约、无 API Key 的 CLI 流程、错误/超时/额度限制。
2. 候选阶段不下载全文；缺失摘要/团队时结果仍合法且不编造。
3. arXiv 多版本和跨主题去重、分页断点、已入库排除、延迟入库归因。
4. 下载不算采纳，入库成功幂等；收藏、浏览、未采纳不变成负标签。
5. 多用户隔离，个人画像和推荐理由不进入公共缓存。
6. 节点离线、服务重启、租约过期、迟到结果与恢复补跑无重复发布。
7. 预算预留和并发控制，未知费用不显示为零，无隐式付费 fallback。
8. 长期兴趣仍占主要地位；探索和补漏不会突破数量或相关性约束。

## 9. 分阶段实施建议

| 阶段 | 主要改动 | 可独立验收的结果 |
| --- | --- | --- |
| 1. 数据与真实反馈 | 论文统一身份、画像快照、个人批次、入库/浏览事件及迁移 | 不调用 AI 也能追踪推荐到入库，正确去重和隔离 |
| 2. 可解释基础推荐 | 长期/近期画像、多路 arXiv 检索、文本与标签排序、历史补漏 | 基础个性化闭环可运行，有可比较的基线 |
| 3. 统一 AI 任务 | 新任务绑定、结构化特征/精排、缓存与预算 | 本地 CLI 默认流程通过；显式 API 配置运行同一契约 |
| 4. 常驻节点执行 | 本地持久化队列、worker、租约、心跳、站内故障状态 | 后端运行时自动生成；迁移常驻主机后可脱离桌面，离线可见、恢复可补跑 |
| 5. 产品与周期更新 | 桌面/手机精选和解释、当前课题、入库状态、参数更新与评估 | 周一/三/五定时精选，真实采纳反馈影响后续版本 |

预计涉及 `backend/services/`、`backend/routers/cloud.py`、论文入库/同步路径、`backend/models.py`、`backend/cloud_models.py`、`supabase/migrations/`、`model_gateway/`、桌面与手机推荐页面及相关测试。远端 worker 建议作为可独立启动的进程，而非依赖桌面应用存活。

本地推荐表自动创建；可选云模式才需要执行数据库迁移。遵循项目测试和 PR 要求；不修改已有认证文件，不直接变更生产部署，不合并 PR。

## 10. 审阅结论与后续边界

首版交付的是基于内容和个人正反馈的多阶段推荐系统：AI 负责有界的特征提取和精排解释，程序负责检索、过滤、调度、采纳记录及参数更新。跨用户协同、自动策略试验、专属模型训练和全文候选分析不在已确认范围内。

执行节点的具体机器、安装版本、服务身份以及可用模型配置，待实施时在用户授权范围内核对；不从现有本地配置推断远端已经配置完成。人民币预算、CLI 额度与模型调用耗时也必须用实际计费模式和小规模测试核实。

参考：本次使用的公开 [grill-me 技能](https://github.com/lrstanley/skills/blob/master/grill-me/SKILL.md)；[Codex 非交互执行官方文档](https://learn.chatgpt.com/docs/non-interactive-mode)，其中包含结构化输出和调用用量事件说明。


## 11. 首版落地说明（以此为准）

- 桌面后端自动启动本机节点；退出时停止。独立 SQLite 保存六张推荐表，原有知识库不迁移、不要求云同步。可从页面停止或重新启动；未来 SSH 主机尚未部署。
- 桌面精选走 `/api/recommendations/personal`，只允许 loopback 访问；该子应用的本地身份不会覆盖云路由认证。公共论文和手机精选仍使用原有云服务，不与本机状态自动同步。
- arXiv 检索采用 30 天重叠窗口，每个检索词最多两页近期结果加一页历史结果，任务级租约重试。未实现逐页持久化游标；失败重跑窗口且按 base ID 去重，极高产主题可能漏掉窗口内后续页。
- 固定内容排序使用词项、作者映射与正反馈，无 embedding 依赖。中文课题可供 AI 精排理解，但首版 arXiv 检索词仅从英文画像词项生成；建议课题同时提供英文关键词。
- 先粗排 30 篇，再按多样性选最多 12 篇做一次 AI 精排及公共特征提取（真实本机 30 篇调用触发 240 秒超时，因此缩小短名单）；公共特征只允许原文片段，用户评分/解释不共享。缓存支持基础结果展示和内容变更失效；AI 重排仍逐批调用，未实现特征缓存命中后的独立抽取跳过。
- 约 7/2/1 名额为软约束；缺少某路候选时回填相关论文。探索来自粗筛剩余的相邻候选，未训练单独的探索模型。
- AI 无效输出立即降级，不额外调用模型重试；任务传输失败最多三次。订阅 CLI 与付费 API 分开，无法识别为 ChatGPT 登录的 CLI 不调用；不把 CLI 调用记为零费用。
- API 使用运维配置的价格上界，调用前保守预留，成功或失败均不退回预留。未接真实账单结算，界面显示预留上界；无价格则仅基础排序。
- 画像和参数版本保留在批次快照，可通过 `/profile/versions` 与 `/profile/rollback` 恢复历史反馈参数。当前知识库和手动课题继续有效；无自动质量退化检测。
- 节点状态区分在线/离线与模型不可用，CLI 认证、额度等详细原因需节点诊断；首版不解析所有 CLI 错误类别，也不采集完整 token 账单。
- 180 天清理仅适用于公共元数据缓存，采纳事件和批次长期保留。真实 14 天采纳率需上线积累，不用合成用例替代。
